# 任务二：管道通信程序（pipe_ipc）

## 1. 任务目标
实现一个基于 Linux 匿名管道的进程间通信程序，完成父子进程之间的数据传递。

本实验在基础通信上进一步实现为“双向通信模型”：
- 父进程循环发送多条请求
- 子进程循环读取请求直到读到 EOF
- 子进程对每条请求返回响应（请求-响应模型）

对应源码文件：pipe_ipc.c

---

## 2. 什么是管道（Pipe）
管道是 Linux 提供的一种 IPC（进程间通信）机制，本质是内核中的一段缓冲区。

主要特点：
1. 先进先出（FIFO）
2. 适合具有亲缘关系的进程（如父子进程）
3. 匿名管道通常单向通信

由于单个匿名管道是单向的，所以本实验使用两个管道实现双向通信：
1. p2c：父进程 -> 子进程（发送请求）
2. c2p：子进程 -> 父进程（发送响应）

---

## 3. 程序实现思路
1. 创建两个管道：p2c 和 c2p。
2. 调用 fork 创建子进程。
3. 父进程：
   - 关闭不用的读写端
   - 循环发送多条请求
   - 关闭发送端，通知子进程 EOF
   - 循环读取子进程响应并打印
4. 子进程：
   - 关闭不用的读写端
   - 循环读取父进程请求，直到 fgets 返回 NULL（EOF）
   - 每次读取后构造响应并写回父进程
5. 父进程 waitpid 回收子进程。

---

## 4. 关键系统调用/函数
1. pipe：创建管道
2. fork：创建子进程
3. close：关闭不需要的管道端
4. fdopen：将文件描述符转换为流，便于按行读写
5. fgets / fprintf / fflush：按行收发请求与响应
6. waitpid：回收子进程

## 7. 实验要点与易错点
1. 一定要关闭不用的管道端，否则可能导致读端无法正确收到 EOF。
2. 父进程发送完请求后要关闭 p2c 写端，子进程才能结束读取循环。
3. 读写双方都应检查错误返回，避免阻塞或异常退出难定位。

---

## 8. 验收总结（可直接口述）
本实验使用两个匿名管道实现了父子进程双向通信。父进程循环发送多条请求，子进程循环读取直到 EOF 并逐条响应，完整演示了基于管道的请求-响应通信模型。

## 9. 详细验收细节

### 9.1 验收前检查清单
1. 可单独编译：`make pipe_ipc`。
2. 运行不依赖额外参数：`./pipe_ipc`。
3. 程序退出码为 0，且父子进程都能正常退出。

### 9.2 现场验收步骤（建议顺序）
1. 编译并运行：`make pipe_ipc && ./pipe_ipc`。
2. 观察父进程发送多条请求日志（`parent sent`）。
3. 观察子进程处理后回传响应（`parent received`）。
4. 说明父进程关闭写端触发 EOF，子进程读取循环结束。

### 9.3 预期验收现象
1. 至少 3 条请求被连续发送。
2. 每条请求都对应一条响应，不丢条、不重复。
3. 程序能自动结束，不会停在阻塞状态。

### 9.4 通过判据（建议口述）
1. 双管道方向明确：`p2c` 请求、`c2p` 响应。
2. 子进程确实“循环读取直到 EOF”，不是只读一次。
3. 父进程有 `waitpid` 回收子进程，生命周期完整。

### 9.5 常见扣分点
1. 忘记关闭无用端，导致读端永远等不到 EOF。
2. 只实现单向发送，不是请求-响应模型。
3. 子进程只读一次，不满足“循环读取直到 EOF”。
4. 缺少错误处理，异常时直接崩溃。
